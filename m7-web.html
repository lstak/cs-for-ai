Module 7

How the Web works

Module 6 showed how computers send packets. The Web is the most successful service built on top of that: a few simple agreements (URLs, HTTP, HTML) that let any browser show any site. Almost every AI product you use is a web app or is reached through a web API, so this module explains the pieces: what a request looks like, what a website is made of, where pages are built, and how programs talk to each other.

1. The Internet is the roads; the Web is the shops

The Internet (Module 6) is the global network that carries packets. The Web is one service that runs over it, built on three agreements:

  • URLs: a way to name anything (https://example.com/docs/intro).
  • HTTP: a way to ask for it and get a reply.
  • HTML: a way to describe pages so any browser can show them, with links between them.

Email, SSH, video calls and online games also use the Internet but aren't "the Web". A browser is simply a program that speaks HTTP, understands HTML, CSS and JavaScript, and draws the result on your screen.

2. HTTP: the conversation

HTTP is a plain-text request → response protocol, carried over the TCP/TLS connection from Module 6. The client (browser, Python script, phone app) sends a request; the server sends exactly one response. A request has a method (what to do), a path (to what), headers (extra information) and sometimes a body (data). A response has a status code, headers and usually a body.

MethodMeaningTypical use
GETRead something. Must not change anything.Load a page, fetch data
POSTSend data to be processed or to create somethingSubmit a form, send a chat message to an AI
PUT / PATCHReplace / partly update somethingEdit a record
DELETERemove somethingDelete a note
StatusFamilyExamples
1xxInformation101 Switching Protocols (used by WebSockets, section 8)
2xxSuccess200 OK · 201 Created
3xxGo somewhere else301 moved permanently · 302 redirect · 304 not modified (use your cached copy)
4xxYou made a mistake400 bad request · 401 not authenticated · 403 forbidden · 404 not found · 429 too many requests
5xxThe server has a problem500 crashed · 502/503 overloaded or down · 504 timed out

Two ideas make the Web work at scale:

  • Stateless. The server treats every request on its own, remembering nothing. So how does a site know you're logged in? On login the server sends a small token in a cookie (Set-Cookie header); your browser automatically attaches it to every later request to that site (Cookie header). Apps that call APIs use an Authorization header with a key instead. (Same reason a chat app must resend the whole conversation: Module 6.)
  • Caching. Headers like Cache-Control: max-age=300 allow the browser (or a nearby CDN, a network of copy servers) to reuse a response instead of asking again. This is the Module 2 "keep a copy closer" idea applied to the network.

HTTP has evolved: HTTP/1.1 (text, one request at a time per connection), HTTP/2 (many requests at once on one connection) and HTTP/3 (over UDP/QUIC to cope better with lost packets, Module 6). The ideas above stay the same.

3. A website: three languages, three jobs

A web page is a bundle of files in three languages. Analogy: a house. HTML is the structure (walls, rooms, doors), CSS is the look (paint, furniture, layout), and JavaScript is the behaviour (lights switching on, doors opening).

HTMLCSSJavaScript (JS)
JobWhat is on the page: headings, text, links, images, buttons, formsHow it looks: colours, fonts, spacing, layout, phone vs desktopWhat it does: react to clicks, change the page, talk to servers
Kind of languageMarkup: tags around content (<h1>Hello</h1>), not a programming languageRules: "every h1 is blue"A real programming language, like Python but different syntax; runs inside the browser
Without itNothing to showPlain but usable pageA static page that never changes

The browser parses the HTML into a tree of objects called the DOM (Document Object Model), applies the CSS rules to it, and paints pixels. JavaScript can then change the tree (add a chat bubble, hide a menu) and the browser redraws only what changed, with no reload. That is the whole trick behind interactive pages.

4. Web servers

A web server is a program that waits on a port (443 for HTTPS, Module 6), reads each incoming HTTP request, and returns a response. Servers come in layers:

PieceJobExamples
Static file serverHands out files as they are: HTML, CSS, JS, imagesnginx, Apache, a CDN, python -m http.server
Reverse proxy / load balancerThe front door: handles HTTPS (TLS), spreads requests over several app servers, cachesnginx, cloud load balancers (Module 12)
Application serverRuns your code for each request: look things up, call a database or an AI model, build a responsePython (FastAPI, Flask, Django), Node.js, Java
DatabaseStores data durably (Module 2): users, documents, chats. See Module 8 for formats, SQL, Postgres and NoSQLPostgreSQL, SQLite, vector databases (Module 11)

Static means the response is a ready-made file, the same for everyone. Dynamic means code builds the response per request. The site you are reading right now is served by python -m http.server, a static server in one command. A dynamic server in a few lines (this is a real, runnable FastAPI app):

# app.py      pip install fastapi uvicorn      run:  uvicorn app:app --reload
from fastapi import FastAPI
app = FastAPI()

@app.get("/hello")                       # GET /hello?name=Ada
def hello(name: str = "world"):
    return {"message": f"Hello, {name}!"}  # becomes JSON: {"message": "Hello, Ada!"}
# open http://127.0.0.1:8000/hello?name=Ada   (and /docs for an auto-made API page)

5. Where is the page built? SSR, CSR and SPAs

When you open a page, someone has to turn data (a user's notes, a list of products, a chat history) into HTML. There are three main choices:

ApproachWho builds the HTML?What the browser first receivesStrengthsWeaknesses
Server-side rendering (SSR)The server, for each request (PHP, Django, Rails, Next.js server mode)A finished page with contentContent appears fast; works well for search engines and link previews; works even on weak phonesServer does work for every view; every click is a full round trip for a new page (unless enhanced)
Client-side rendering (CSR)The browser, using JavaScriptAn almost empty HTML shell plus a JavaScript bundle; the JS then fetches data from an API and builds the pageApp-like and smooth; servers only serve files and JSONBlank screen until JS downloads and runs; slow on weak devices; search engines and previews may see nothing
Single-page application (SPA)The browser (CSR taken further)Loads once; afterwards JS swaps parts of the page and only fetches small JSON, never reloadingFeels like a desktop app (Gmail, chat apps, editors)Big first download; you must manage the URL/back button and state in JS
Static / pre-renderedA build step, once, ahead of timeA finished page from a CDNFastest and cheapest; trivial to scaleSame for everyone; changes require a rebuild

Modern frameworks (Next.js, Nuxt, SvelteKit) mix them: the server renders the first view, then the browser "hydrates" it (JS attaches behaviour to the existing HTML) and behaves like an SPA afterwards. This course site is the simplest kind: static files plus a little JavaScript.

6. APIs, JSON and REST

An API (application programming interface) is a menu of things one program lets other programs do. A web API puts that menu on the Web: instead of returning a page for humans, the server returns data for programs, almost always as JSON (JavaScript Object Notation), a simple text format of keys and values that every language can read:

{"id": 42, "text": "Buy milk", "done": false, "tags": ["home", "urgent"]}

REST is a popular style for designing web APIs:

  • Resources are nouns, in the URL. /notes is the collection, /notes/42 is one note.
  • HTTP methods are the verbs. GET read, POST create, PUT/PATCH update, DELETE remove.
  • Status codes report the result (201 created, 404 missing, 400 bad input).
  • Stateless and self-contained: each request carries everything needed (including the key).
RequestMeaningSuccess
GET /notesList all notes200 + list
POST /notes + JSON bodyCreate a note201 + the new note
GET /notes/42Read note 42200 or 404
PATCH /notes/42 + JSON bodyChange note 42200
DELETE /notes/42Remove note 42204 (no body) or 200

Not everything is strictly REST. Many AI APIs are one "do this" endpoint, such as POST /v1/chat with a JSON body (Module 6). That is closer to a remote procedure call (RPC), but it uses the same ingredients: HTTP, JSON, an API key, status codes. Other styles you'll meet: GraphQL (the client asks for exactly the fields it wants through one endpoint) and gRPC (fast binary calls between servers). Good APIs also use versions (/v1/), pagination (?limit=20&page=2) and rate limits (429).

7. Calling an API from a page or a program

Browser JavaScript uses fetch; Python uses requests (Module 6). Same request, different language:

// JavaScript in a web page
const r = await fetch("/api/notes", {
  method: "POST",
  headers: {"Content-Type": "application/json"},
  body: JSON.stringify({text: "Buy milk"}),
});
const note = await r.json();                  // {"id": 3, "text": "Buy milk"}
document.querySelector("#list").append(note.text);   // update the DOM: no page reload
# Python
import requests
note = requests.post("http://127.0.0.1:8000/notes", json={"text": "Buy milk"}, timeout=10).json()

8. Real time: polling, server-sent events and WebSockets

Plain HTTP is "client asks, server answers". The server can't speak first. For live features (chat, streaming AI replies, notifications, multiplayer, live collaboration) there are three techniques:

TechniqueHow it worksGood for
PollingThe client asks "anything new?" every N secondsSimple, rare updates. Wasteful and delayed (the same trade-off as polling vs interrupts, Module 9)
Server-sent events (SSE)The client makes one ordinary HTTP request; the server keeps the response open and writes pieces into it over time (Content-Type: text/event-stream). One direction: server → clientStreaming AI replies, live feeds, progress bars
WebSocketsThe client asks to upgrade the HTTP connection; both sides then keep a two-way channel open and send small messages whenever they likeChat between users, games, collaborative editing, live voice and "realtime" AI

9. Putting it together: a chat web app

 You open https://chat.example.com
 1. Browser ──GET /──────────────▶ reverse proxy ─▶ static server       ← HTML shell, CSS, JS bundle   (Modules 6, 7)
 2. JS runs (this is an SPA) ─────GET /api/me (cookie)─▶ app server     ← "who am I?" as JSON
 3. You type and press Enter. JS ──POST /api/chat {"message": "..."}──▶ app server
 4. App server (holding the secret AI key; the browser never sees it)
      ──POST https://api.ai-provider.example/v1/chat (stream)──▶ AI model on GPUs   (Modules 10, 12)
 5. Tokens stream back ◀── SSE chunks ◀── app server ◀── provider
 6. JS appends each chunk to the page (DOM); the browser repaints. No reload.        (Module 9: the screen)

Why the extra hop in step 4? Because anything sent to the browser can be read by the user (press F12). If the page's JavaScript held your AI provider key, anyone could copy it and run up your bill. The server keeps the secret and also enforces limits, logging and permissions.

Quick ways to put an AI model behind a web page without writing HTML: Gradio and Streamlit are Python libraries that start a web server for you and generate the page.

10. Security basics for web apps

RuleWhy
Use HTTPS everywhereEncrypts the conversation (TLS, Module 6); otherwise cookies, keys and chats can be read on the way.
Keep secrets on the serverThe browser is the user's territory. Never put API keys in page JavaScript or in a public repo.
Never trust input from the clientAnyone can send any request with curl, ignoring your page's buttons. Validate everything on the server, check permissions on every request.
Don't insert untrusted text as HTMLCross-site scripting (XSS): if a page inserts text as HTML, an attacker's <script> runs in other users' browsers. Model output is untrusted text too: a manipulated model (prompt injection, Module 13) can write such code. Insert text as text (element.textContent), sanitise any HTML.
Protect cookiesHttpOnly (JS can't read it), Secure (HTTPS only), SameSite (not sent on cross-site requests).
Understand CORSA browser rule: a page from site A may only read responses from site B if B's server says so (Access-Control-Allow-Origin). The "CORS error" in the console is the browser protecting users; fix it on the server, not in the page.
