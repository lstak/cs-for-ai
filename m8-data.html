Data: storage & manipulation

AI is made of two ingredients: a model and data. Models learn from data, and every AI product stores something: users, conversations, documents, logs, embeddings. Choosing how to store data (which file format, which database) decides how fast you can work, how much it costs, and whether your system stays correct when many people use it at once. This module gives you the map.

  • Tell structured, semi-structured and unstructured data apart.
  • Choose between CSV, JSON, JSON Lines, Parquet and other formats, with reasons.
  • Explain row-oriented vs column-oriented storage and why Parquet is fast for analytics.
  • Filter, group and join data with pandas and with SQL.
  • Explain what a database management system does (Postgres, SQLite, DuckDB), including transactions (ACID) and indexes.
  • Compare SQL and NoSQL (key–value, document, wide-column, graph) and vector databases, and pick one for a given job.
  • Describe where the data lives in typical AI systems (training sets, chat apps, RAG), and the basics of data quality and safety.

1. Kinds of data

Everything is bits (Module 1), but how those bits are organised matters:

Data has a life cycle: collect → store → clean → transform → use (train, analyse, serve) → keep or delete. Most of the real work in AI projects happens in the "clean" and "transform" steps, which is why the manipulation tools in this module matter so much. And "garbage in, garbage out": a model can only be as good as the data it learned from.

2. File formats

A file format is an agreement about how to write data into bytes. The same table can be written in many formats, each with different strengths. The four you'll meet most often:

Why is Parquet so much faster? Rows vs columns

Storage is a long sequence of bytes. You must choose the order in which to lay a table out in it:

  • Row-oriented (CSV, JSON, most databases' tables): all values of row 1, then row 2, and so on. Perfect when you want whole records ("show me user 42").
  • Column-oriented (Parquet, analytics databases): all values of column 1, then column 2. Perfect when you want a few columns across many rows ("average tokens per request"). Values in a column are alike, so they also compress very well (for example, a column that has only "small" or "large" is stored as a short dictionary plus tiny codes).

Disks and networks read data in blocks (Module 2). Reading a block costs the same whether you need one value or all of it, so a layout that puts the values you need next to each other means fewer blocks.

3. Manipulating data

Most data work is a short list of operations, whatever the tool: load, select columns, filter rows, group and aggregate, join tables, sort, save. In Python the standard tool is pandas (or the faster Polars); in databases the same operations are written in SQL. Learn to think in operations, and you can switch between them.

import pandas as pd

df = pd.read_csv("requests.csv", parse_dates=["time"])       # load  (a table called a DataFrame)
df.head(); df.dtypes; df.isna().sum()                        # look: first rows, column types, missing values per column

ok = df[df["status"] == "ok"]                                 # filter rows
stats = ok.groupby("model")["tokens"].agg(["count", "mean"])  # group + aggregate
df = df.merge(users, on="user", how="left")                   # join with another table

df.to_parquet("requests.parquet", index=False)                # save as Parquet (needs pyarrow)
slim = pd.read_parquet("requests.parquet", columns=["model", "tokens"])   # read only 2 columns!

The same operations in SQL (which you can also run directly on files with DuckDB: SELECT ... FROM 'requests.parquet'):

SELECT model, COUNT(*) AS n, AVG(tokens) AS avg_tokens
FROM requests
WHERE status = 'ok'
GROUP BY model;

4. Database management systems

You can keep everything in files. But files don't help when many people read and write at once, when you want one quick answer out of a billion rows, or when a crash happens halfway through an update. A database management system (DBMS) is software that stores data on disk and takes care of those jobs for you. Analogy: a librarian. You don't walk the shelves yourself; you ask, and the librarian finds the book, makes sure two people don't borrow the same copy, and keeps the records safe if the power fails.

A DBMS provides: durable storage (Module 2), a query language (you say what you want and it decides how to get it), indexes for speed, transactions for correctness, access control (who may see what), and backups.

Relational databases and SQL

A relational database stores tables. Each table has typed columns and many rows. A primary key identifies each row uniquely; a foreign key in another table points to it. This lets you store each fact once and join tables when you need them together. The language is SQL (Structured Query Language), over 40 years old and still the most useful data skill there is.

-- A schema for a chat app (PostgreSQL)
CREATE TABLE users    (id SERIAL PRIMARY KEY, email TEXT UNIQUE NOT NULL);
CREATE TABLE chats    (id SERIAL PRIMARY KEY, user_id INT REFERENCES users(id), title TEXT);
CREATE TABLE messages (id SERIAL PRIMARY KEY, chat_id INT REFERENCES chats(id),
                       role TEXT NOT NULL, content TEXT NOT NULL, tokens INT,
                       created_at TIMESTAMPTZ DEFAULT now());
CREATE INDEX ON messages (chat_id);                         -- make "all messages of chat X" fast

SELECT c.title, COUNT(*) AS n_messages, SUM(m.tokens) AS total_tokens
FROM chats c JOIN messages m ON m.chat_id = c.id            -- join: combine rows that match
WHERE c.user_id = 42
GROUP BY c.title
ORDER BY total_tokens DESC;

Transactions and ACID: don't lose the money

A transaction groups several changes into one all-or-nothing step. Moving €10 from Ann to Bob is two updates (subtract, add). If the power fails between them, the money vanishes. Relational databases promise ACID:

  • Atomicity: all the steps happen, or none do.
  • Consistency: rules (keys, NOT NULL, checks) are never broken by a committed transaction.
  • Isolation: simultaneous transactions don't see each other's half-finished work.
  • Durability: once the database says "committed", the change survives a crash (it is written to disk, Module 2).
BEGIN;
UPDATE accounts SET balance = balance - 10 WHERE owner = 'ann';
UPDATE accounts SET balance = balance + 10 WHERE owner = 'bob';
COMMIT;      -- or ROLLBACK; to undo everything

Indexes: the book's index

Without help, finding user 7,000,001 means reading every row until you hit it (a full scan). An index is a separate, sorted structure (usually a B-tree) that lets the database jump almost directly to the row: a few page reads instead of millions. The price: extra disk space, and every write must update the index too. Index the columns you search and join on, not everything.

Client–server: Postgres runs as a server process listening on a port (5432 by default, Module 6). Your application server (Module 7) connects with a driver using a connection string, sends SQL, and receives rows back, much like an HTTP request but with its own protocol. The database holds the data and the permissions; the application never reads its files directly.

# Try SQLite right now (no installation; it ships with Python)
import sqlite3
con = sqlite3.connect("app.db")                         # creates the file if needed
con.execute("CREATE TABLE IF NOT EXISTS messages (id INTEGER PRIMARY KEY, chat_id INT, role TEXT, content TEXT)")
con.execute("INSERT INTO messages (chat_id, role, content) VALUES (?, ?, ?)", (1, "user", "What is DNS?"))
con.commit()                                            # make it durable (end the transaction)
for row in con.execute("SELECT role, content FROM messages WHERE chat_id = ?", (1,)):
    print(row)
# Try PostgreSQL in a container (Module 5), then talk to it
docker run --name pg -e POSTGRES_PASSWORD=change-me -p 5432:5432 -d postgres:16
psql -h localhost -U postgres                     # an interactive SQL shell
# Python:  pip install "psycopg[binary]"  ·  psycopg.connect("postgresql://postgres:change-me@localhost:5432/postgres")

SQL injection. Never build SQL by gluing user text into a string: f"SELECT * FROM users WHERE name = '{name}'". If a user types x' OR '1'='1 the query returns every user (and worse). Always use parameters (? or %s placeholders, as in the code above) so the database treats the input as data, never as commands. This is one of the most common web security holes (Module 7), and the same lesson applies to anything an AI model writes into a query (Module 13).

OLTP vs OLAP

Two very different workloads need two designs: OLTP (online transaction processing) means many small reads and writes of individual records, such as a web app, handled by row-oriented databases like Postgres. OLAP (online analytical processing) means a few huge queries that scan and aggregate millions of rows, such as "average cost per model per day over a year", handled by columnar systems such as Parquet + DuckDB or a warehouse. It is the rows-vs-columns idea again.

5. NoSQL: beyond tables

"NoSQL" (really "not only SQL") covers databases that don't use the relational table model. They were created to handle huge scale, very flexible data, or access patterns that tables handle poorly. Several families:

FamilyData modelExamplesTypical AI-era uses
Key–valueA giant dictionary: key → value, looked up by key only. Extremely fast, often in RAMRedis, DynamoDB, MemcachedCaching answers, sessions, rate limits, counters
DocumentJSON-like documents grouped in collections; no fixed schemaMongoDB, Firestore, CouchDBChat transcripts, product catalogues, user profiles with varying fields
Wide-columnHuge, sparse tables partitioned across many machines, optimised for very high write volumeCassandra, HBase, BigtableTime series, telemetry, activity feeds at massive scale
GraphNodes and relationships; queries follow connectionsNeo4j, NeptuneSocial networks, fraud rings, knowledge graphs
Search engineInverted index for full-text search and filtersElasticsearch, OpenSearchKeyword search over documents and logs
Vector databaseStores embeddings (Module 11) and finds the nearest ones to a query vectorpgvector (in Postgres), Qdrant, Chroma, Pinecone, FAISSSemantic search and RAG: "find the document chunks closest in meaning to this question"

The trade-offs behind the choices:

  • Schema flexibility vs guarantees. Document stores let each record look different, which is quick to start with but moves rule-checking from the database into your code. Relational databases make you design the structure up front and then enforce it.
  • Scaling out. Many NoSQL systems were built to shard (split) data across many machines. A single Postgres server can already handle a great deal (many millions of rows and thousands of requests per second), and managed or distributed variants go further, so don't reach for scale you don't need.
  • Consistency vs availability. When the network between a distributed database's machines breaks (Module 6), it must choose: stay consistent (some requests are refused) or stay available (replies might be stale). Many NoSQL systems choose eventual consistency: all copies agree, soon. Banks need strong consistency; a "likes" counter doesn't.

A good default: start with PostgreSQL. It handles tables, JSON (JSONB) and, with pgvector, embeddings, all in one system with strong guarantees. Add a specialised store (Redis for caching, a warehouse for analytics) when you can name the problem it solves. This is a rule of thumb, not a law: serious scale or very special access patterns can justify something else.

7. Keeping data safe and correct

  • Back up, and test restoring. A common rule is 3 copies, on 2 kinds of storage, with 1 off-site. A database that cannot be restored is not a backup.
  • Encrypt data in transit (TLS, Module 6) and at rest (on disk), and keep passwords and keys out of data files and code.
  • Least privilege. Give each application the minimum database permissions (an AI feature that only reads should have a read-only account).
  • Validate input at the edge (Module 7) and use parameterised queries.
  • Decide retention. Keep only what you need, and for as long as you need it. Chat logs and training data often contain personal information.
  • Version your data like code: know which dataset (and which cleaning) produced which model.
