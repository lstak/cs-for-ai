Life of an AI request

Time to put every layer together. You type a question into a chatbot and press Enter. A second or two later, words start to appear. We'll follow that one message from your keyboard, across the network, through a GPU in a data centre, and back to your screen, and see which part of this course explains each step.

  • Explain why a reply streams, why a big model is slower than a small one, and why a long prompt delays the first word.
  • Read an error message and name the layer it came from.
  • See how other AI jobs (images, speech, search, training) use the same layers differently.

2. Where does the time go?

From the story you can already predict the waiting. Some delays come from distance (the speed of light, Module 6), some from queueing, some from reading your prompt (lots of parallel maths, Module 3), and the rest from writing the answer one token at a time (reading every weight from memory per token, Modules 2 and 3). The model's size and number format (Module 1) decide how many GPUs it needs and how quickly it can write.

Interactive: the timeline of one chat request

Illustrative numbers for one request on typical data-centre GPUs (80 GB each, ~1 TB/s usable memory bandwidth, ~150 TFLOP/s usable). Real services batch many users and use other tricks, so treat the output as a model of why, not a benchmark. Try: a 70B model, a 30,000-token document, a server on the other side of the planet.

Three things this timeline explains: (1) Streaming exists because the whole answer can take many seconds, but the first word only needs the first four stages, so showing words as they appear makes it feel instant. (2) A long prompt (pasting a whole document) delays the first word, because all of it must be processed before writing begins. (3) A bigger model needs more GPUs and writes more slowly: it has more weights to read for every single token. That is also why providers offer small, fast models and large, slow ones.

3. Same layers, different AI jobs

Chat is only one shape. The layers are the same; what flows through them differs:

4. Training in the same picture

Everything above is using a finished model. Training (and its cheaper cousin, fine-tuning) is the same machinery in a loop that also changes the weights (Module 11):

  1. Read a batch of examples from storage (Module 2) and turn them into numbers (Module 1).
  2. Copy the batch to the GPU and run it through the model.
  3. Measure how wrong the output was, work out how to nudge every weight, and apply the nudge.
  4. Repeat millions of times, saving a checkpoint (a copy of the weights) every so often so a crash doesn't lose days of work.

It needs several times more GPU memory than using the model, because the corrections must be stored too (Module 1), and it can run for days or weeks on many GPUs talking over very fast links. The pipeline idea applies: if the GPU sits idle, something upstream (slow storage, slow data preparation) isn't feeding it fast enough. In practice most people use an existing model and either call it via an API or fine-tune it briefly, rather than training from scratch.

5. Reading errors by layer

You now have a map. When something fails, ask: which layer is complaining?

What you seeLayerWhat it means
401 UnauthorizedAPI / account (Modules 6, 12)Missing or wrong API key
429 Too Many RequestsAPI service (Modules 6, 12)Rate limit. Wait and retry with increasing delays
Connection timed out / Connection resetNetwork (Module 6)The packets did not get through in time. Check connectivity, region and timeouts
"Prompt too long" / "maximum context length"The model (Module 11)Your conversation plus the answer would exceed the context window. Shorten, summarise, or retrieve only the relevant parts
CUDA out of memoryGPU memory (Modules 2, 3)The model plus the conversation does not fit in VRAM. Use a smaller or quantised model
Killed (no explanation)Operating system (Module 4)RAM ran out; the OS OOM-killed the process
No space left on deviceDisk (Module 2)Often a big model download filled the disk
ModuleNotFoundError, CUDA version mismatchEnvironment / drivers (Module 5)Wrong or missing packages or driver versions
A fluent, confident, wrong answerThe model, not the computer (Module 11)Nothing is broken: it produced a plausible continuation. Add sources, tools or checking (Module 13)
An agent loops or does something unwantedThe agent design (Module 13)Step limits, permissions and approval steps are missing
