Module 12

The cloud

"The cloud" is not a place or a mystery. It is other people's computers in big data centres, rented by the hour (or by the request) through a web interface or API. Almost every AI product you use runs there. This module shows what you can rent, how it connects to everything you've learned, and how to avoid a surprise bill.

  • Explain what cloud computing is and the main building blocks (compute, storage, network, managed services).
  • Choose between renting a GPU machine and calling a hosted model API, with a back-of-envelope cost.
  • Explain regions, availability zones, and why location matters (latency, law, price).
  • Recognise the usual traps: idle GPUs, data-transfer fees, leaked keys.

1. What "the cloud" actually is

Analogy: electricity. You don't run your own power station; you plug in and pay for what you use. Cloud providers (Amazon Web Services, Microsoft Azure, Google Cloud, and others) run enormous data centres full of servers and let you rent slices of them in seconds.

Where the analogy breaks: electricity is the same everywhere. Cloud resources differ by region, by hardware type and by availability. Good GPUs are often scarce and you may have to request a quota or wait.

Under the hood it is still everything from Modules 1–10: a rented "virtual machine" is a Linux (or Windows) computer (Module 4) with a CPU, RAM, maybe a GPU (Modules 2–3), that you reach over the network (Module 6), typically through ssh.

3. Regions, zones and why location matters

  • Region: a geographic area with several data centres (e.g. "Frankfurt", "Virginia").
  • Availability zone: one data centre (or group) inside a region; spread over zones so one fire or power cut doesn't take you offline.

Choose a region for: latency (Module 6: light needs ~1 ms per 200 km each way, so Amsterdam to Virginia (about 6,200 km) is at least ~60 ms round trip, and typically 75–90 ms in practice), law (some data must stay in the EU), price (varies by region) and GPU availability.

4. Rent a GPU, or call an API?

You have two broad options for using an AI model in a product:

  • Call a hosted model API. Zero setup, pay per token, always the latest model, no idle cost. You depend on a provider and send them your data.
  • Self-host an open model on a rented GPU. You pay per hour whether or not anyone is using it, and you handle scaling, updates and monitoring. Can win at high, steady volume or when data may not leave your control.

Key idea: an API bills for work done; a rented GPU bills for time reserved. At low or spiky volume, API usually wins because you aren't paying for idle hardware. At high steady volume the GPU can win, if you keep it busy. This "utilisation" idea (how busy the expensive hardware is kept) is what the capstone's timeline hints at, now measured in dollars.

5. Common traps

TrapWhat happensHabit that prevents it
Forgotten GPU instanceA GPU left running over a weekend can cost hundreds of dollars.Stop/terminate when done; set budget alerts and auto-shutdown.
Data-transfer ("egress") feesMoving data out of the cloud (or between regions) is billed per GB.Keep data and compute in the same region.
Leaked secret keysAPI keys or cloud credentials pushed to a public repo get found by bots within minutes and abused.Never commit keys; use environment variables or a secrets manager; give each key the minimum permissions.
Spot / preemptible instancesMuch cheaper GPUs that the provider can take back on short notice.Save checkpoints often so a job can resume.
Quotas & availability"No GPUs available in this region" or a quota of zero for new accounts.Request quota early; try another region or GPU type.

Who is responsible for what?

The provider secures the building and hardware; you secure what you put in it: who may log in, which ports are open (Module 6), whether the storage bucket is accidentally public. This is called the shared responsibility model.
