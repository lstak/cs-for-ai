From code to hardware

Your Python line reply = model.generate(prompt) passes through half a dozen layers of software before a single transistor flips. Knowing the layers tells you what an AI "model" actually is as a piece of software, where it comes from, and where errors originate.

1. Machine code and languages

The CPU only understands machine code: raw binary instructions specific to its architecture (x86-64 in most PCs/servers, ARM in phones and Apple chips). Humans write in higher-level languages and a translator converts them:

ApproachHowExamplesTrade-off
CompiledTranslate the whole program to machine code before runningC, C++, Rust, GoFast to run; slower to develop
InterpretedA program (the interpreter) reads your code and does what it says, line by linePython, JavaScript (mostly)Easy and flexible; 10–100× slower per operation
JIT-compiledCompile hot parts while runningNumba, torch.compile, JAXBest of both, with warm-up cost

CPython (the standard Python) is itself a C program. It converts your code to bytecode, then loops over the bytecode doing checks for every operation ("is this an int? a list?"). That per-operation overhead is why a Python for loop over a million numbers is slow.

2. Why NumPy and PyTorch are fast

They're not written in Python. They're Python wrappers around pre-compiled C/C++/CUDA code. When you call np.sum(a) Python makes one call, and the whole million-element loop then runs in optimised compiled code, often using SIMD instructions (Module 3). This is why AI work is written in Python (easy to read and glue together) while the heavy lifting runs in compiled code. A good habit: express data work as whole-array operations rather than Python loops.

import numpy as np, time
xs = list(range(5_000_000)); a = np.arange(5_000_000)
t = time.time(); s = 0
for v in xs: s += v * 2             # interpreter does work per element
print("python loop", time.time() - t)
t = time.time(); s = (a * 2).sum()  # one call into compiled code
print("numpy      ", time.time() - t)   # typically 30-100x faster

4. Libraries, packages and environments

Nobody writes everything from scratch. A library is reusable code; a package is a library you install (pip install torch) from an index (PyPI). Libraries depend on other libraries, which depend on specific versions of others. Project A needs torch 1.13, project B needs torch 2.3: they can't share one installation. Solutions:

  • Virtual environment (python -m venv .venv, conda, uv): a private folder of packages per project.
  • Container (Docker): bundles the app and its libraries and OS-level files into one portable image, which runs identically on your laptop, a cluster and the cloud. It's like a lightweight, isolated mini-computer sharing the host's kernel (not a full virtual machine).
  • Version pinning (requirements.txt, lock files): record exact versions so results are reproducible.
python -m venv .venv && source .venv/bin/activate   # make + enter a private environment
pip install numpy torch
pip freeze > requirements.txt                        # record exact versions
python -c "import torch; print(torch.__version__, torch.cuda.is_available())"

The GPU stack: your app → AI library (PyTorch) → GPU libraries (CUDA, cuBLAS) → NVIDIA driver (OS-level) → GPU. Each layer must be compatible with the next. "CUDA version mismatch", torch.cuda.is_available() == False and "driver too old" are all layer compatibility problems, not bugs in the model.

5. The AI software ecosystem: what's what

When people say "the model", they usually mean a file of numbers (the weights from Module 1) plus a little configuration. To use it you need software that knows how to read the file and run the maths. The pieces:

PieceWhat it isExamples
FrameworkA library for building and running neural networks; does the matrix maths on CPU or GPU (Module 3)PyTorch, JAX, TensorFlow
Model file (weights)The learned numbers, saved to disk. Different formats suit different tools; "safe" formats can't hide executable code, unlike Python's older pickle files.safetensors, .gguf (quantised, for laptops), .pt
Model hubA website that hosts models and datasets so you can download them, like an app storeHugging Face Hub
Inference engineA program specialised to run a model quickly (loading weights, generating tokens, handling several users)llama.cpp, Ollama, vLLM
Hosted APISomeone else runs the engine; you send requests over HTTPS (Module 6) and pay per use (Module 12)Claude API, other providers
ApplicationThe product people use, built on one of the aboveA chatbot, a coding assistant, a photo-tagging app
# Two ways to get a reply. Same idea, different layers.

# 1) Local: you run the model (needs the weights downloaded, ~GBs, and enough RAM/VRAM)
from transformers import pipeline
chat = pipeline("text-generation", model="some-small-model")     # downloads + loads the weights
print(chat("Explain RAM in one sentence.", max_new_tokens=40))

# 2) Hosted: someone else runs it; you send an HTTPS request (see Module 6 and Module 13)

Don't run unknown code or weights blindly. Downloading a model or package is running someone else's software on your computer. Prefer well-known sources, safe weight formats, and read what an installer wants to do. This theme returns in Module 13 (agents and tools).
