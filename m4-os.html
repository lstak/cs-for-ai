The operating system

The operating system (Linux, Windows, macOS) is the manager that sits between your programs and the hardware. It shares one machine among many programs, keeps them from trampling each other, and gives them a simple view of files, memory and devices.

1. What the OS is for

  • Share the CPU: dozens of programs "run at once" on a handful of cores by taking turns very quickly (scheduling).
  • Share memory safely: each program thinks it owns a private, huge block of memory (virtual memory). It can't read another program's data.
  • Provide files and devices: you call open(); the OS talks to the SSD via a driver. Same for network, GPU, keyboard.
  • Enforce permissions: who may read which file, who may use the GPU.

Programs ask the OS for services through system calls (read, write, fork, socket…). The core of the OS that does this is the kernel. Everything else (the shell, the desktop) is just programs.

2. Programs, processes, threads

  • Program: a file on disk with instructions (python, train.py).
  • Process: a running instance: its own memory, open files, and an id (PID). Two copies of Python running = two processes.
  • Thread: a separate flow of execution inside a process, sharing its memory. Cheap to create, but can corrupt shared data if careless.

A local chatbot is several processes. Run a chat model on your own laptop and you will find a model server process (it holds the 14 GB of weights), your chat app (a browser tab or terminal), and maybe a vector database for your documents. They talk to each other through the network stack on localhost (Module 6). Start the model server twice and you load the weights twice. Python can also start extra worker processes (rather than threads, because its "GIL" lets only one thread run Python code at a time), and each one needs its own memory.

3. Scheduling: taking turns

With 100 processes and 8 cores, the scheduler gives each process a short time slice (a few milliseconds) and then switches to the next. A context switch saves one process's state and loads another's. Switching isn't free. Short slices feel responsive, but waste time on switching.

Interactive: the scheduler

Three processes (A, B, C) want CPU time on a single core. Compare "first come, first served" with "round robin" and adjust the time slice and switching cost.

Notice with first-come-first-served, C has to wait for A and B to fully finish before it even starts. Round robin lets everyone start early (good for interactive use) at the price of extra switches. Real schedulers are cleverer, but this trade-off is the heart of it.

4. Virtual memory, swap and the OOM killer

Each process sees its own virtual address space; the OS and hardware map it to real RAM in 4 KB pages. Benefits: isolation, and the ability to pretend there's more memory than there is. When RAM runs short, the OS can push rarely-used pages to disk (swap), which is ~1000× slower than RAM, so the machine suddenly crawls ("thrashing"). If swap also fills, the kernel's OOM killer picks a process (usually the biggest) and terminates it. You just see Killed in the terminal.

Interactive: fill up the RAM

Machine: 16 GB RAM + 8 GB swap. Launch programs and watch the system state. Click a segment to close that program.

When your local model won't start: "Killed" with no explanation usually means the OS ran out of RAM and OOM-killed the process while it loaded the weights. "CUDA out of memory" is a different thing: the GPU's memory is too small and the AI library raised a normal error. The cure is the same in spirit: choose a smaller or quantised model (Module 1). Knowing which layer complained tells you which memory to fix.

5. Talking to the OS: system calls, commands, the shell, the terminal and GUIs

So far the OS has been the manager that shares the machine. But how do you, or a program, actually ask it for something? There are several layers between your fingers and the hardware, and people often mix up their names (terminal, shell, command, "the console"). Once you see how they stack, the confusion disappears.

The stack

Everything you do ends up as the same thing: a program asking the kernel for a service. The kernel exposes a fixed menu of requests called system calls (open, read, write, fork, exec, socket…). That menu is the operating system's API (application programming interface, Module 7: the same idea as a web API, but between programs and the kernel). On top of it sit ordinary programs: commands like ls and cat, and graphical applications like a file manager. A shell lets you start commands by typing; a terminal is the window you type in; a desktop lets you start apps by clicking.

Analogy: a restaurant. The kitchen is the kernel. The order slip in a fixed format is the system call. Chefs who each cook one dish are the commands. The waiter who understands your spoken order and passes it to the right chef is the shell; the table where you sit and talk is the terminal. A restaurant with a touchscreen menu is the GUI: a different way to place the same orders. Where it breaks: a chef can't call another chef directly in a restaurant, but commands can be wired together (below).

The small tools: ls, cat, grep and friends

Unix-style systems (Linux, macOS, WSL2) come with hundreds of small commands built on one philosophy: each tool does one thing well, reads and writes plain text, and tools can be chained. A few you will use constantly:

How commands are wired together

  • Arguments and flags. In grep -n ERROR server.log, grep is the command, -n is a flag (option), and ERROR and server.log are arguments.
  • Three standard streams. Every process starts with stdin (input, stream 0), stdout (normal output, 1) and stderr (error messages, 2). By default stdin is your keyboard and stdout/stderr are your screen.
  • Pipes (|) connect the stdout of one command to the stdin of the next: cat server.log | grep ERROR | wc -l means "take the log, keep the error lines, count them". The kernel provides the pipe (a small in-memory channel, Module 2).
  • Redirection sends a stream to or from a file: > overwrite, >> append, < read from, 2>&1 merge errors into normal output. python train.py > log.txt 2>&1 saves everything the script prints.
  • Wildcards. ls *.csv: the shell expands *.csv into the matching file names before ls even starts. ls never sees the star.
  • PATH. When you type ls, the shell searches the folders listed in the PATH variable for a program file called ls. That is why a freshly installed tool sometimes is "command not found": its folder is not in PATH.
  • Exit codes. Every command ends with a number: 0 means success, anything else means failure or "nothing found". The shell stores it in $?, and scripts use it. (grep returns 1 when nothing matches.)
  • Builtins. A few commands, such as cd, are part of the shell itself and not separate programs. They have to be: a child process cannot change its parent's current folder.

What is really happening: strace

On Linux you can watch the system calls a command makes with strace (on macOS, sudo dtruss; on Windows, the Process Monitor tool). This is a trimmed, illustrative result for cat notes.txt:

strace -e trace=execve,openat,read,write,close cat notes.txt

execve("/usr/bin/cat", ["cat", "notes.txt"], ...) = 0          # the shell started the program
openat(AT_FDCWD, "notes.txt", O_RDONLY) = 3                    # ask the kernel for the file; get back file number 3
read(3, "buy milk\nlearn SQL\nbuy coffee\n...", 131072) = 52   # the kernel copies 52 bytes into the program
write(1, "buy milk\nlearn SQL\nbuy coffee\n...", 52) = 52      # print them: file number 1 is stdout
close(3) = 0

So cat is a 5-line story: open the file, read it, write it to the screen, close it. ls asks the kernel to list a directory (openat then getdents64), and grep reads like cat but writes only the matching lines. Commands are thin: the kernel does the real work.

GUIs: the same services with a different front door

A graphical file manager looks nothing like ls, yet to list a folder it asks the kernel for exactly the same thing. The extra layers are about input and output: a window system turns mouse movements into "click on that icon", and graphics libraries turn the list of names into pixels (Module 1, the GPU in Module 3). Underneath, it's the same OS API. That's why it doesn't matter whether you create a folder by right-clicking or by typing mkdir.

Why the terminal matters for AI practitioners. Cloud and lab GPU machines are usually headless: no screen, no desktop, only a shell reached by SSH. Every tutorial, README and error message assumes you can type commands. And AI coding agents (Module 13) use a shell too: the model writes a command, the program around it runs it, and the output goes back to the model. That is why permission prompts for shell commands are so important: a command can delete files just as easily as it can list them.

On Windows: PowerShell offers the same ideas with different names: Get-ChildItem (alias ls/dir) lists files, Get-Content (alias cat) prints a file, Select-String works like grep, and pipes connect them, but PowerShell passes objects, not just text. The easiest way to follow Unix tutorials on Windows is WSL2 (next section), which gives you a real Linux shell. Careful: rm -rf deletes recursively with no confirmation. Check the path twice, and prefer ls first to see what you are about to delete.

6. Linux, macOS, Windows and WSL2: same job, different flavours

What they all share. Every mainstream OS has a kernel, processes and threads, a scheduler, virtual memory, a file system with permissions, drivers, a shell, and a TCP/IP network stack. Everything in sections 1–5 is true on all of them, and Python behaves almost the same. The differences are in the details below.

How the families relate

  • macOS and Linux are cousins. Both follow Unix conventions (POSIX): similar commands (ls, cd, grep, ssh), the same /-separated paths, and the same permission model. Most tutorials for one work on the other.
  • Windows is a different lineage. Different kernel, backslash paths with drive letters, a different shell, and different ways of starting processes. Old Windows scripts and Linux scripts rarely run unchanged.
  • WSL2 is the bridge. It is not an emulator: Windows runs a genuine Linux kernel in a small, fast virtual machine, so inside WSL2 you really are on Linux. This is a common way to get a Linux workflow on a Windows laptop with GPU support.
  • Containers (Docker) are Linux technology. On macOS and Windows, Docker quietly starts a Linux VM underneath. That's another reason "develop anywhere, but deploy on Linux" is the usual advice.

Practical gotchas for AI work

  • Where you keep files in WSL2 matters. Your project in the Linux home (~/project) is fast. The same project under /mnt/c/... has to cross between two file systems and can be many times slower (Module 2: many small reads across a file-system boundary are slow).
  • Case sensitivity. Linux treats Data.csv and data.csv as different files; Windows and macOS (by default) treat them as the same. Code that works on your laptop can fail on a Linux server.
  • Line endings. Windows text files often end lines with two characters (CRLF), Linux with one (LF). A shell script saved with Windows endings can fail on Linux with confusing errors.
  • Worker processes. Windows and macOS start new Python processes from scratch ("spawn"); Linux has traditionally used the cheaper "fork" (the default is shifting in newer Python versions). Practical effect: for DataLoader(num_workers>0) or multiprocessing, put your main code under if __name__ == "__main__": or Windows/macOS may crash or recursively start workers.
  • Paths in code. Use pathlib.Path("data") / "train.csv" instead of gluing strings with / or \.
uname -a                  # Linux/macOS/WSL2: which kernel am I on? (WSL2 shows "microsoft" and "WSL2")
cat /etc/os-release       # which Linux distribution (Ubuntu, Debian, ...)
wsl --list --verbose      # run in Windows PowerShell: which WSL version does each distro use?
nvidia-smi                # GPU visible? (works in WSL2 if the Windows NVIDIA driver is installed)

Rule of thumb: prototype wherever you're comfortable (Windows, macOS, WSL2), but expect the servers that host AI models, and cloud machines (Module 12), to run Linux, so avoid OS-specific habits in your code and test there early.

1) Open htop (or Task Manager) while running a Python loop while True: pass. Which number goes to ~100%? Now start 4 copies. What happens on a 4-core machine? (An AI model running flat out looks much the same: it uses every core or the whole GPU you give it.)

2) In the scheduler widget find a time slice and switch cost where round robin finishes later on average than first-come-first-served, yet still has the best "first response" time. Why can that be a good trade for a laptop (typing in a chat window while a model runs in the background) but not for one big overnight job?

3) Open a terminal. Use ls -l to see the files in your home folder, cat to print a small text file, and grep -n to find a word in it. Then redo the same task with the graphical file manager. Which layers did you use in each case, and which did they have in common?

4) In the mini shell, count how many ERROR lines are in data/server.log in three different ways (hint: grep -c; a pipe into wc -l; and reading the output yourself). Then save only the error lines to errors.txt and print that file.

5) On Linux/WSL2, run strace -e trace=openat,read,write cat notes.txt 2>&1 | head (install strace if needed). Which system call opened the file? Which call printed the text to the screen?

6) A teammate says "the terminal is the shell". Correct them in two sentences using the layer diagram.

7) Run uname -a (and cat /etc/os-release) on your machine. Which OS family and kernel are you really on? If you're on Windows, run wsl --list --verbose in PowerShell as well and compare the two. Then predict: would /mnt/c/Users exist here, and why?
