Module 6

Networking

Computers talk by chopping data into small packets, addressing each one, and letting a web of routers forward them. Layers of agreed rules (protocols) turn that unreliable mess into something that feels like a clean pipe.

  • Explain IP addresses, ports, DNS, TCP vs UDP, HTTP and what an API call really does.
  • Describe what is actually sent when you chat with an AI service, and why replies stream.
  • Calculate a minimum network delay from distance, and explain why latency matters more than bandwidth for many small requests.
  • Describe how packets are split, reordered, lost and retransmitted.

1. The layers

LayerJobExamples
ApplicationWhat the programs say to each otherHTTP(S), SSH, gRPC, DNS
TransportWhich program on the machine; reliabilityTCP (reliable, ordered), UDP (fast, no promises)
InternetWhich machine; routing across networksIP addresses (IPv4/IPv6)
Link / physicalOne hop over a cable, Wi-Fi or fibreEthernet, Wi-Fi, 5G
  • IP address: a machine's number (e.g. 93.184.216.34), like a building's street address.
  • Port: which program (door) at that address: 443 = HTTPS, 22 = SSH, 80 = HTTP, 8888 = Jupyter by default.
  • DNS: the internet's phone book, turning names (example.com) into IP addresses.
  • Router: forwards packets hop by hop toward the destination; it doesn't know the entire path.

2. Packets

Data is cut into packets (≈1,500 bytes). Each carries source, destination and a sequence number. They may take different routes, arrive out of order, or get dropped when a router is overloaded. TCP fixes this: it numbers packets, the receiver acknowledges them, missing ones are retransmitted, and the data is reassembled in order. UDP just sends and hopes; it's used where speed beats perfection (live video, games, voice).

3. Anatomy of a web request

When you (or your Python code) fetch https://api.example.com/v1/predict a whole conversation happens before you get a byte of the answer:

  1. DNS lookup: ask a resolver for the IP of the name.
  2. TCP handshake: SYN → SYN-ACK → ACK to open a reliable connection (one round trip).
  3. TLS handshake: agree on encryption keys for HTTPS (one more round trip).
  4. HTTP request/response: GET /v1/predict → 200 OK + data (one round trip plus the server's thinking time).

Each step costs at least one round-trip time (RTT), bounded by the speed of light in fibre (about 200,000 km/s, i.e. 200 km per millisecond, so 1 ms of RTT per 100 km one way). No amount of bandwidth can beat physics.

4. What a chat with an AI really sends

When you press Enter in a chat app, the app (not the model) sends an HTTPS request to the AI provider's server (the steps above), usually a POST with a small JSON body: the conversation so far, a few settings, and a secret API key in a header that proves who you are (and who gets billed). The server runs the model and sends back the reply.

POST https://api.example-ai.com/v1/chat          # illustrative URL
Authorization: Bearer sk-...your secret key...
{
  "model": "some-chat-model",
  "max_tokens": 300,
  "temperature": 0.7,
  "messages": [
    {"role": "user", "content": "Explain DNS in one sentence."}
  ]
}
import requests, os
reply = requests.post("https://api.example-ai.com/v1/chat",
    headers={"Authorization": "Bearer " + os.environ["AI_API_KEY"]},   # key from an environment variable, never in the code
    json={"model": "some-chat-model", "max_tokens": 300,
          "messages": [{"role": "user", "content": "Explain DNS in one sentence."}]},
    timeout=60)                                                         # always set a timeout
print(reply.status_code, reply.json())

Things that follow from how the network works:

  • The whole conversation is sent every time. The server doesn't remember you between requests (HTTP is "stateless"), so the app re-sends earlier messages, and longer chats mean bigger requests and more tokens to process (Modules 11 and 13).
  • Replies stream. The model produces one token at a time (Module 11), so the server keeps the connection open and sends each piece as soon as it exists. You start reading after the first token arrives (network latency + the model's start-up), instead of waiting for the whole answer.
  • Status codes tell you what went wrong. 200 OK · 401 bad API key · 429 too many requests (rate limit: wait, then retry with a growing delay) · 500/503 the server is struggling · timeouts mean the network or server is too slow (Module 6, above).
  • Secrets travel in headers over TLS. That is why API keys must stay in environment variables or a secrets store, never in code you share (Module 12).
  • Location matters. A server 100 ms away adds 100 ms before anything happens; for an app that chains several AI calls (Module 13), those add up. Regions are covered in Module 12.
  • SSH (port 22, encrypted) is how you log into a remote machine; scp/rsync copy files, such as a model's weights.
